# 09. Платформа, инструментирование, рандомизация, клиентские эксперименты (гл. 4, 12, 13, 14, 16)

## Компоненты платформы (гл. 4)
1. **Определение и управление:**
   - владелец, описание, даты, итерации (исправления, раскатка кольцами);
   - история, сравнение draft и running;
   - валидация конфликтов и таргетинга;
   - **запустить может только владелец, остановить — любой** (асимметрия вреда).
   - Для Fly: автоматическая раскатка, NRT-мониторинг, **автоматическое выключение** плохих экспериментов.
2. **Деплой и назначение вариантов:**
   - f(hash(ID)) — детерминированно, консистентно, независимо;
   - одна реализация сервиса назначения;
   - атомарность: родительский сервис назначает вариант и передаёт его дочерним;
   - **одна точка назначения** на ранних фазах.
   - Архитектуры: (1) code fork `if variant==T` — проще триггеринг, но растёт техдолг; (2) параметры; (3) конфиг, переданный вниз по потоку — производительнее, сложнее триггеринг (Google, Bing).
   - Office передаёт bug ID как параметр и через 3 месяца напоминает удалить код.
   - Мерить накладные расходы самой платформы — часть трафика держать вне её.
3. **Инструментирование:** логировать вариант **и итерацию** для каждого запроса; **контрфактические логи** для триггера; фидбек пользователей с ID варианта.
4. **Анализ:** cooking данных → метрики по сегментам → p-values и CI → **проверки доверия первыми** → визуализация.

### Параллельные эксперименты
- **Single-layer (numberline):** 1000 бакетов, каждый пользователь в одном эксперименте. Просто, но трафик ограничен. **Мониторить характеристики бакетов**; перемешивать бакеты между экспериментами (carryover).
- **Пересекающиеся слои:** layer ID в хеше даёт ортогональность.
  - Full factorial: все во всех экспериментах; риск коллизий (синий текст × синий фон).
  - **Nested:** слои по зонам системы (header, body, backend, ranking).
  - **Constraints-based:** graph coloring.
  - Автоматическая детекция взаимодействий (Microsoft).

## Клиентские эксперименты (гл. 12)
- **Релиз:** app store review, пользователи обновляются неделями, одновременно живут несколько версий. Staged rollout в store нельзя анализировать как эксперимент: видно только, кто обновился.
- **Связь:** офлайн, Wi-Fi-only телеметрия, батарея, CPU, память, размер приложения.
- **Выводы:**
  1. **Заранее параметризовать:** feature flags, dark features, серверная конфигурация. Пример: Windows 10 через год после релиза тестировала текст поиска в таскбаре — миллионы долларов.
  2. **Отложенное логирование и старт:** конфиг применяется со следующей сессии; около недели на стабилизацию adoption; ранние данные смещены к активным пользователям и Wi-Fi; разный эффективный старт при shared control. Окно сравнения выбирать аккуратно.
  3. **Failsafe:** кешировать назначение; вариант по умолчанию при офлайне; OEM first-run; стабильный ID до и после входа.
  4. **Триггер:** назначение фетчится для всех экспериментов сразу, отсюда over-triggering. Отправлять событие при фактическом использовании.
  5. **Guardrails устройства и приложения:** батарея, CPU, отключения push, размер приложения, краши (clean exit → телеметрия при следующем старте).
  6. **Релиз целиком** — квазиэксперимент с поправкой на adoption bias (Xu & Chen 2016).
  7. **Несколько устройств:** разные ID → разные варианты; переходы app ↔ web.

## Инструментирование (гл. 13)
- **Клиент** — что видит и делает пользователь: действия, производительность, ошибки и краши. Цена — CPU, батарея, JS увеличивает латентность. **Beacons теряются** (гонка с загрузкой новой страницы); синхронный redirect надёжнее, но медленнее (для рекламных кликов выбирают надёжность). **Никогда не вычитать клиентское время из серверного.**
- **Сервер** — меньше дисперсия, детали системы (скоры ранжирования, дата-центр). Синхронизировать часы.
- **Join key** во всех логах, общий формат (timestamp, страна, язык, платформа).
- **Культура:**
  - ничего не выходит без инструментирования;
  - сломанное логирование = сломанная фича;
  - тестировать логи в разработке;
  - мониторить сырые логи (объёмы по измерениям, инварианты, выбросы).

## Единица рандомизации (гл. 14)
- Уровни: страница, запрос, сессия (30 минут бездействия), **пользователь**, user-day.
- **Критерии:**
  1. **Консистентность опыта:** чем заметнее изменение, тем крупнее единица.
  2. **Метрики.**
- Мелкая единица — больше единиц, меньше дисперсия, но нельзя использовать, если:
  - фичи действуют через границы единицы (персонализация, переформулировка запроса);
  - метрики считаются через границы (сессии на пользователя при рандомизации по странице);
  - пользователь замечает разные варианты (SUTVA).
- **Единица рандомизации = единице анализа или крупнее.** Рандомизация по пользователю и CTR по страницам требует delta method или bootstrap; одиночный бот с 10,000 просмотров перекашивает результат. Решение — ограничить вклад пользователя или взять CTR-per-user. Пользовательские метрики при рандомизации по странице бессмысленны.
- Другие сценарии: enterprise-тенанты, рекламодатели и их кластеры, кластеры друзей.
- **Пользовательские ID:**
  - signed-in ID — кросс-девайс и стабилен;
  - cookie — псевдоним, теряется;
  - device ID — стабилен, но идентифицирует человека.
  - Онбординг через логин тестировать на cookie или device ID. Долгосрочные эффекты — на долгоживущем ID.
  - **IP — только для инфраструктурных тестов** (хостинг): гранулярность нестабильна, NAT корпораций.

## Масштабирование анализа (гл. 16)
- **Cooking:**
  1. сортировка и join логов;
  2. очистка — боты, фрод, дубли, «нарушающие законы физики» сессии. Фильтр может удалить больше событий в одном варианте и дать SRM;
  3. обогащение — браузер, день недели, переходы между экспериментами.
- **Вычисление:** per-user таблица + join с назначением, или метрики прямо в пайплайне эксперимента. В обоих случаях — **общие определения метрик**.
- **NRT-путь** (простые суммы для алертов и автовыключения) + batch-путь.
- **Визуализация:**
  - SRM и ключевые тесты сверху, **ExP прячет scorecard при провале**;
  - OEC и критичные метрики, относительные изменения, цвет значимости;
  - drill-down по сегментам; общий эффект рядом с триггерным;
  - подписки на метрики;
  - согласование с владельцами метрик при негативе.
- Группы метрик:
  - LinkedIn: компания / продукт / фича;
  - Microsoft: Data quality / OEC / Guardrail / Local-diagnostic.
  - Пороги p ниже 0.05 для фильтрации; BH; «метрики интереса»; связанные метрики (CTR вырос из-за кликов или из-за меньших просмотров?).
