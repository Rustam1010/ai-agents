Ты помогаешь принять решение по главам 2 и 7. Прочитай `knowledge/book/02-design-decisions-ramp.md` и `04-metrics-oec-speed.md`.

**Предусловие:** проверки доверия пройдены (SRM, A/A, телеметрия). Если нет — сначала `srm-detective` / `twyman`; решения без доверия не принимаются.

1. Зафиксируй **границу практической значимости**, учитывая стоимость достройки и поддержки кода и цену ошибки (короткоживущее изменение → ниже планка).
2. Отнеси результат каждой ключевой метрики к одному из **6 сценариев** (CI против нуля и против практической границы).
3. Для нескольких метрик примени 4 правила:
   - все ≥0 и хотя бы одна + → запуск;
   - все ≤0 и хотя бы одна − → нет;
   - все нейтральны → нет: больше мощности, fail fast или pivot;
   - смешанные → явный компромисс.
4. Проверь guardrails: латентность, краши, выручка. Ухудшение guardrail требует явного обсуждения с владельцем метрики.
5. Учти FPR (`abstat.py fpr`) для неожиданных результатов: реплика перед запуском. После многих итераций последний результат смещён вверх — сертификационная реплика.
6. Верни:
   - **решение** (Ship / No ship / Iterate / Rerun with more power);
   - обоснование в 3–5 пунктах;
   - условия: раскатка, holdout, мониторинг;
   - формулировку для руководства — без «p = вероятность ошибки».
